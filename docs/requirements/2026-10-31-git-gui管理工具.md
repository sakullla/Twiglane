# 需求：Twiglane（枝序）Git 桌面客户端

日期：2026-10-31

本文整理已确认的产品方向与基于调研形成的首版需求建议，作为后续设计、开发与验收的需求基线。用户已确认面向个人开发者和小团队，首版支持 macOS 与 Windows；具体功能取舍依据简洁、实用和 UI/UX 质感目标形成，不代表用户逐项指定了这些功能。

## 一屏摘要

- 目标与使用者：Twiglane（枝序）为个人开发者和小团队提供操作简单、功能实用、视觉精致的 Git 桌面客户端（R1、R18）。
- 平台：首版交付 macOS 与 Windows 客户端，并在两个系统验证日常操作闭环（R1）。
- 范围：仓库接入、差异查看、暂存提交、远程同步、分支、历史、临时保存改动、合并冲突和有限操作恢复（R2—R11）。
- 关键行为：明确当前仓库、分支、提交范围及同步结果；操作失败保留可继续工作的状态（R3—R11、R14）。
- 体验：围绕当前任务安排界面，采用一致的字体、间距、图标和状态表达，兼顾鼠标与键盘操作（R12—R14）。
- 成功标准：用户能在 GUI 内完成克隆、部分提交、推送以及分支合并与冲突处理；两个系统结果一致且失败可继续处理（R1、R5—R7、R10）。
- 首版假设：中文优先，采用标准 Git 暂存语义，支持标准 HTTPS/SSH 仓库，本地操作不依赖平台登录（R3、R5、R13）。
- 首版暂缓：内置研发平台业务、游戏资源专用管理及 AI 聊天，集中打磨日常 Git 工作流（R15—R17）。

## 完整需求

### R1 产品定位与双平台交付

行为：面向需要频繁查看改动、提交代码、切换分支和同步远程的个人开发者与小团队，交付可安装、可启动、可实际操作本地 Git 仓库的 macOS 与 Windows 桌面客户端。以完成日常任务和理解操作结果为主要体验目标。

适用与失败边界：两个系统均属于首版交付范围。安装或启动缺少必要条件时，应说明缺失条件及处理方式。具体兼容的系统版本与硬件范围应在交付说明中明确，不以单一系统上的演示替代双平台验收。

验收：

- 在交付说明列明的 macOS、Windows 环境分别安装和启动客户端，可打开真实仓库。
- 在两个系统分别完成“克隆 → 查看差异 → 选择部分改动 → 本地提交 → 推送”，本地提交内容及远程结果与操作选择一致。
- 在两个系统分别完成创建分支及合并；出现冲突时能够进入 R10 规定的处理流程。

### R2 仓库接入与快速切换

行为：支持添加已有本地仓库、通过地址克隆仓库及在选定目录新建仓库；提供最近使用的仓库列表、搜索和切换入口。仓库展示名称与路径，帮助区分同名项目。

适用与失败边界：路径无效、目录无法访问、目标不是仓库或克隆目标目录不可用时，解释原因；不得覆盖现有文件或擅自把普通目录初始化为仓库。克隆失败应说明本地是否存在未完成内容以及可继续采取的操作。

验收：

- 添加真实本地仓库后可查看状态；重新启动后可从最近列表再次打开。
- 输入可访问的远程地址与可用目录后可克隆；选择目录并明确执行新建后生成可用仓库。
- 添加两个同名、路径不同的仓库，可辨认并切换；操作目标随切换更新。
- 输入无效路径或使用存在冲突的克隆目录时显示原因，已有文件保持原状。

### R3 仓库连接与认证

行为：以支持标准 HTTPS、SSH Git 仓库作为首版需求假设，不依赖特定托管平台的专有快速提交能力。显示当前远程名称和地址，支持配置及修改远程地址；本地查看、暂存、提交和分支操作不要求登录第三方平台。

适用与失败边界：访问私有仓库所需的凭据或 SSH 条件由实际仓库决定。认证失败、权限不足或地址不可达时，区分原因并给出可执行的处理指引。缺少认证时不得将远程操作显示为成功，也不得因此阻止无须联网的本地操作。认证及错误界面不得显示完整敏感凭据。

验收：

- 对具有访问权限的 HTTPS 和 SSH 测试仓库分别完成远程访问；修改远程地址后展示的目标与实际操作一致。
- 未登录托管平台时，仍可查看本地仓库并创建本地提交。
- 使用无权限或失效认证信息访问私有仓库时，显示认证或权限问题，修正后可重试。

### R4 改动列表与差异查看

行为：展示本地新增、修改、删除等文件变化，支持按路径或名称查找文件；选择文本文件后显示其差异，并提供统一与并排对照方式。差异区域优先保障内容阅读，路径、行号和增删状态可辨认。

适用与失败边界：二进制或无法直接预览的文件，应显示文件状态及无法预览的说明，不伪装成无差异。耗时的差异加载要有反馈，读取失败不得导致整个仓库界面失去响应。仓库或文件在外部改变后，应刷新到当前状态，避免让用户依据过期内容提交。

验收：

- 在同一仓库创建、修改和删除文件后，列表及差异与实际变化一致。
- 在两种差异模式间切换，选择的文件不丢失，增删内容对应同一份变化。
- 选择二进制文件时能够知道该文件有变动，并看到预览能力边界。
- 通过外部编辑器修改已打开文件后，客户端反映更新后的内容。

### R5 标准暂存与明确提交范围

行为：采用标准 Git 暂存语义作为首版需求假设。支持按文件及文本差异中的代码块暂存、取消暂存，并明确区分未暂存与已暂存内容。提交区显示当前目标分支和本次范围；本地提交与“提交并推送”应能明确区分，用户可只提交到本地。

适用与失败边界：没有可提交内容或未填写提交说明时，提示用户补充。提交检查失败、文件读取失败或提交未成功时，保留说明及仍然有效的暂存状态并解释原因。提交成功但推送失败应分别报告两个阶段的结果，不要求用户重复创建同一提交。外部 Git 工具形成的暂存内容必须如实展示。

验收：

- 在一个文本文件中准备两个可独立暂存的改动块，只暂存其中一块后提交；提交仅包含该块，另一块仍保留在工作区。
- 暂存后继续修改同一文件，可分别辨认已暂存和未暂存的变化。
- 选择只提交到本地后，出现本地提交且没有自动推送；选择提交并推送后，界面分别反映提交与推送结果。
- 提交检查失败时，修正问题后可继续使用原提交说明；推送失败后可单独重试推送。

### R6 远程检查、拉取与推送

行为：提供检查远程变化、拉取和推送入口；区分检查远程信息与修改本地分支的动作。显示待拉取、待推送状态，以及远程信息最后检查时间；没有上游分支时提供明确的发布或关联引导。

适用与失败边界：远程状态依赖最近一次成功检查，离线或检查失败时不得将其表示为实时确认。推送因远程已有新提交而被拒绝时，解释原因并引导更新处理，不自动强制推送。拉取遇到本地改动或冲突时，应进入保护改动或冲突处理流程，不静默覆盖用户内容。

验收：

- 远程新增提交后，仅检查远程变化，客户端更新远程信息而工作区文件不因此改变。
- 当前分支仅落后远程且可直接更新时，拉取后文件、历史和同步状态一致更新。
- 本地存在未推送提交时显示对应状态；推送成功后远程可见该提交。
- 模拟网络中断、无上游分支及推送被拒绝，分别看到准确状态和下一步入口；失败后可重试。

### R7 日常分支管理

行为：支持查找、创建、切换和删除本地分支，区分本地与远程分支，并持续展示当前分支。用户可从当前状态创建分支，选择分支后明确执行切换；合并行为由 R10 规定。

适用与失败边界：分支名称无效或重复时给出原因。切换可能覆盖未提交改动时，应提示并提供先保存改动的路径。不能删除当前分支；删除包含尚未合入当前分支的提交的分支前，应明确说明风险并由用户主动决定。

验收：

- 创建新分支并切换后，顶部状态、历史范围和后续提交目标均更新为该分支。
- 对无效或重复名称的创建请求，显示失败原因且不生成意外分支。
- 准备会阻碍切换的本地改动后执行切换，可看到保护改动的处理方式，原内容不被静默丢弃。
- 尝试删除当前分支时不能执行，并说明原因。

### R8 提交历史与文件历史

行为：提供独立历史视图，以列表或分支图表达提交关系；支持按提交说明、作者或提交标识查找。选择提交后可查看说明、作者、时间、文件列表及差异；可从文件进入该文件的修改历史。

适用与失败边界：空仓库、没有匹配记录或文件没有可用历史时显示对应空状态。仅查看历史不能改变当前分支、工作区或暂存区。已删除文件的历史记录仍应能展示其提交差异。

验收：

- 在含多个分支与提交的仓库中，能够找到已知提交并查看对应文件变化。
- 查看某个文件的历史，可定位该文件的一次修改并查看当次差异。
- 切换查看不同历史提交后，当前工作区内容及分支保持原状。
- 搜索无结果时明确显示无匹配记录，不显示为加载失败。

### R9 临时保存与恢复改动

行为：支持把尚未提交的改动临时保存，并查看、恢复及删除保存记录。保存前说明覆盖范围，尤其明确是否包含未跟踪文件；恢复后能辨认哪些改动已返回工作区。

适用与失败边界：没有可保存内容时说明原因。未包含的改动不得被清除或被误报为已经保存。恢复与当前工作区冲突时，应说明冲突并提供处理入口；没有成功恢复前不得自动删除原保存记录。删除记录前说明影响。

验收：

- 准备未提交改动，按界面显示的范围保存，切换处理其他工作后可恢复原内容。
- 仓库存在未跟踪文件时，能在保存前辨认它是否包含在内，结果与提示一致。
- 恢复发生冲突时，原保存记录仍可找到，且冲突文件可继续处理。

### R10 分支合并与冲突处理

行为：合并前明确显示来源分支、目标分支和本地改动情况。发生文本冲突后列出冲突文件，并提供本地版本、另一分支版本与合并结果的对照，允许选择或编辑结果，逐项处理后继续完成合并；提供中止合并入口。

适用与失败边界：合并前发现未提交改动可能被影响，应先引导保护改动。二进制冲突说明无法按文本合并，明确用户选择保留哪一版本。中止和继续均应如实反映 Git 当前状态；仍有未解决冲突时不能表示合并已经完成。中止前说明哪些合并中的编辑会被撤销。

验收：

- 两个分支分别修改同一文本位置后合并，显示冲突文件及对应版本，用户能编辑最终结果并完成合并。
- 完成后提交内容与用户确认的合并结果一致，界面不再显示合并进行中。
- 对二进制冲突选择一个版本后，最终文件与选择一致。
- 从受支持的合并状态执行中止，返回合并前分支状态；合并开始前受保护的用户改动仍可找回。

### R11 有边界的操作恢复与放弃改动

行为：支持撤销最近一次尚未推送的普通本地提交，同时保留其文件改动；支持放弃指定文件或明确选定范围的本地改动。操作名称及说明应区别“撤销提交并保留改动”和“放弃文件修改”。

适用与失败边界：不承诺所有 Git 操作都能撤销。最近一次提交已经推送、属于不支持直接撤销的状态或不能可靠判断是否已推送时，不直接提供本地提交撤销，应解释原因。放弃改动前展示影响范围及恢复能力；无法保证恢复的内容明确提示，不静默扩大到未选择文件。

验收：

- 撤销最近一次未推送的普通提交后，该提交从当前分支末端撤回，文件改动仍可查看和再次提交。
- 最近一次提交已推送时，不通过该入口悄悄改写共享历史。
- 选择两个文件中的一个放弃修改，确认后仅该文件恢复，另一个文件保持原内容。
- 取消放弃改动操作后，选定文件保持原状。

### R12 以当前任务为中心的信息架构

行为：默认进入改动视图，以仓库导航、文件列表、差异详情组织主要工作区；顶部稳定展示当前仓库、分支及同步状态。历史单独呈现，提交区与本次改动相邻；低频和高风险操作按当前任务展开，避免与日常操作争夺注意力。主要面板可调整宽度。

适用与失败边界：空仓库、没有改动和没有选择文件时，提供与当前状态相关的说明及下一步入口。长仓库名、分支名和路径不能遮挡关键按钮，应提供查看完整信息的方式。调整窗口或面板大小后，主要内容可通过布局调整或滚动访问。

验收：

- 打开包含改动的仓库后，无需进入设置即可看到当前分支、文件变化、差异和提交入口。
- 从改动切换到历史，再返回改动时，仍可明确辨认当前仓库和分支。
- 使用长路径及长分支名称，并调整窗口和面板宽度，关键操作仍可访问，完整名称可查看。
- 没有本地改动时，不以无解释的空白区域替代状态说明。

### R13 视觉质感与中文表达

行为：采用克制、清晰的桌面工具视觉风格；字体层级、间距、图标、按钮、边框、选中态及浮层保持一致。提供浅色与深色主题，差异区域优先保障代码阅读。中文优先作为首版假设，保留必要 Git 术语并在需要时配合通俗解释。

适用与失败边界：视觉强调服务于当前操作和状态辨认。增删、警告、失败和选择状态不能仅依靠颜色表达，应同时使用文字、符号或明确结构。主题切换不能降低差异内容、禁用说明和焦点的辨识度。

验收：

- 使用同一组包含新增、修改、删除及冲突的内容，分别检查两种主题，可区分状态并阅读差异。
- 在仓库接入、改动、历史、冲突及设置页面检查同类控件，样式和交互状态一致。
- 检查主要操作与错误提示，使用一致的中文术语，能够辨别操作目标及结果。
- 两个系统均检查文字截断、浮层位置、选中态和主题表现，不出现遮挡关键内容的问题。

### R14 操作反馈、键盘使用与失败后继续处理

行为：常用操作提供可发现的快捷键及可见焦点，遵循所在系统的操作习惯。加载和执行过程显示进行状态；成功反馈说明已完成的动作，失败反馈说明失败阶段、原因与可执行下一步。重复触发可能造成重复执行的操作时应有防重入行为。

适用与失败边界：耗时操作不能只表现为无反馈的冻结。失败后保留仍有效的输入和用户改动；涉及主动放弃内容的操作按其确认范围处理。取消与重试入口只在实际支持时展示，不承诺尚不存在的恢复能力。

验收：

- 通过键盘完成文件选择、差异浏览、输入提交说明和触发提交；焦点位置可见，操作目标明确。
- 在克隆或同步期间，能够辨认操作正在执行，重复点击不重复启动同一动作。
- 模拟网络及提交检查失败，能看到失败阶段并在修正后重试，提交说明等有效输入不被无故清空。
- 本地提交成功而推送失败时，明确显示两个阶段的不同结果，重试仅执行尚未成功的推送。

### R18 产品名称与品牌表达

行为：应用命名为 **Twiglane**，中文名为 **枝序**。Twig 表达轻巧的枝条，lane 表达清晰的路径；“枝序”呼应 Git 分支与有序管理，传达轻量、清晰、从容的产品定位。品牌短句为“让每次改动，都清晰有序。”安装展示名称及应用主名称使用 `Twiglane`；中文介绍可使用“枝序”，需求及对外介绍首次出现时使用“Twiglane（枝序）”。

适用与失败边界：命名用于本产品的识别与表达，不改变 Git、分支、暂存、提交等功能术语。Logo、配色和具体品牌图形由后续视觉设计确定。

验收：

- macOS 与 Windows 的安装展示名称、应用主名称及关于信息统一使用 `Twiglane`，中文介绍与需求文档中的名称对应“枝序”。
- 品牌介绍使用完整名称“Twiglane（枝序）”，品牌短句出现时与本条一致。

## 不做事项

以下为基于轻量化目标提出的首版范围取舍，不代表后续版本永久排除这些能力。

### R15 首版暂缓内置研发平台业务

行为：首版不内置 Issue、TAPD、代码评审、合并请求管理及 CI/CD 业务页面，不把这些平台业务作为日常 Git 操作的必经环节。

适用与失败边界：此边界不排除通过标准 Git 协议访问相应平台的仓库；仓库认证和 Git 操作仍按 R3、R6 验收。

验收：

- 用户无需配置研发平台业务模块，就能完成本地工作及远程同步；主导航未混入上述业务页面。

### R16 首版暂缓游戏资源专用管理

行为：首版不交付工蜂锁、Excel 差异合并、游戏引擎资源管理、专用 LFS 加速及多仓库依赖编排能力，优先覆盖普通代码仓库的日常流程。

适用与失败边界：此边界不等于阻止用户查看包含二进制文件的仓库；这些文件仍按 R4、R10 说明预览或合并边界。遇到当前不支持的仓库能力时，应告知限制，不伪报操作成功。

验收：

- 普通仓库使用过程不要求配置资源管理或专有加速服务；界面不提供无法实际交付的专用资源管理入口。

### R17 首版暂缓 AI 聊天

行为：首版不交付 AI 聊天工作区，不以 AI 服务配置作为 Git 操作的前提。

适用与失败边界：此取舍服务于当前任务聚焦和操作可理解性，不扩展为对未来智能辅助能力的永久限制。

验收：

- 用户无需接入 AI 服务或提供 AI 凭据，即可完成全部首版 Git 工作流。

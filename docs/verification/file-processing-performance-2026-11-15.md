# 文件处理性能与内存验证

环境：Windows，Node.js 26.4.0，Rust 1.99.1。基线为 `cce3d58e7044ae9f23af2020cdec8b392499fa5f` 中的文件排序、路径排名和摘要函数，与本次工作区实现比较。

改动位于 `src-tauri/src/git/files.rs`：

- 自然排序借用名称分段，ASCII 名称比较不分配字符串；保留数字、前导零、Unicode 小写转换和大小写平手规则。
- 路径匹配用最大堆保留前 `limit` 条候选，保留原排序、目录派生、忽略标记、扫描计数和截断语义。候选空间从 O(匹配数) 降到 O(limit)，目录集合仍随目录数增长。
- 全文搜索先截取 UTF-8 摘要再分配字符串，避免截短后仍保留整行容量；文件探测前缀直接借用，减少一次复制。

## 局部基准

从两个版本提取实际函数，在独立 Rust 程序中以 `rustc --edition=2021 -O` 编译。同一进程中依次运行基线和优化版本，共三轮，每轮断言结果完全一致。输入构造不计时。耗时取中位数，使用系统分配器；另一次运行包装系统分配器统计额外存活分配字节峰值和分配次数。

| 场景 | 基线耗时 | 优化耗时 | 基线额外堆峰值 | 优化额外堆峰值 |
| --- | ---: | ---: | ---: | ---: |
| 30,000 个 ASCII 名称自然排序 | 564.727 ms | 28.922 ms | 480,720 B | 480,000 B |
| 200,000 条路径，查询 `file`，取前 200 条 | 75.932 ms | 32.695 ms | 11,142,676 B | 76,836 B |
| 2,000 条 64,000 字节长行生成摘要 | 69.759 ms | 0.569 ms | 128,146,000 B | 946,000 B |

排序场景分配次数从 7,391,345 次降到 1 次，剩余分配来自稳定排序的临时数组。峰值接近不代表分配开销接近。

输入构造：排序名称为 `Part{(i*7919)%30000}-file{i%19}.ts`；路径为逆序的 `dir{i%1000}/file{i}.ts`；长行为 `needle` 加 63,994 个 `x`。内存统计排除已构造的输入，包含算法临时集合及返回结果，不含分配器元数据。

这些结果衡量算法局部开销，不代表整个应用的 RSS、磁盘读取或端到端响应时间。未测量 macOS/Linux 或桌面应用整进程内存。

## 二、浏览器观察（headless Chrome + `npm run preview:ui`，mock 数据）

候选 `b10a621` + T6-A3 工作区，视口 1280×840 与 900×600（`Emulation.setDeviceMetricsOverride` 精确设定，`window.innerWidth/Height` 读回一致）：

本轮（T6-A3）重测的条目：两个视口的完全可见行数、标题栏控件计数、无横向滚动、提交区四档高度与失败原因行的四档高度、仓库菜单条目的 `title`。其余条目沿用候选 `b10a621` 的观察，本轮改动只落在提交区一行文本、一条菜单 `title` 与一个新增 class 的颜色上，不经过那些路径。

- 1280×840：`[data-diff-row]` 完全可见 **45 行**（R3 的 40 行成立）；标题栏 `data-titlebar-control` **恰好 6 个**；`scrollWidth = clientWidth = 1280`，无横向滚动。
- 900×600：`scrollWidth = clientWidth = 900`，无横向滚动；rail 已自动折叠（`--sidebar: 56px`）；差异区在文件列表 360px 时宽 447px、160px 时宽 647px；完全可见 `[data-diff-row]` 30 行（R3 只要求 1280×840 下 ≥40 行）。
- 提交区四档实测（文件列表栏宽用分隔条的 `role="slider"` 逐次 −16px 调到 160、读回 `aria-valuenow=160`；360 为 mock 默认值，读回 `.files` 宽度一致）：

  | 视口 | 文件列表栏宽 | `.composer` 高度 | `.composer-meta` 高度 |
  | --- | --- | --- | --- |
  | 1280×840 | 360 | 168px | 24px |
  | 1280×840 | 160 | 168px | 24px |
  | 900×600 | 360 | 168px | 24px |
  | 900×600 | 160 | 168px | 24px |

  四档都守住 R5 的 200px；栏宽 160px 时标题与元信息行仍是 `nowrap` + 省略（标题文本宽度被压到 0，只剩图标、计数与溢出按钮），没有折行顶高。
- 新增的失败原因行不改变上面的高度（这是 T6-A3 唯一可能影响 R5 的改动）：把与生产同形的 `[data-commit-error]`（同标签、同 `hint truncate composer-error` 三个类、同 Rust 措辞的整句）放进 `.composer-meta` 的同一位置后，四档仍全部是 `.composer` 168px / `.composer-meta` 24px，元素自身高 15px、`white-space: nowrap`、`overflow: hidden`（160px 栏宽下可见宽 59px、`scrollWidth 405px` 被省略而不是折行）；颜色读回 `rgb(184, 50, 61)`，即浅色主题的 `--danger-text`。**口径说明**：预览 mock 的 `commitChanges` 永远成功，进不了真实失败态，所以这一项测的是「这一行元素对提交区高度的布局影响」，不是端到端失败态的浏览器证据；失败态本身由下节的 happy-dom 断言覆盖。
- R16 自动折叠阈值：窗口 999px 宽时 `.sidebar.rail` 自动带 `collapsed`（`--sidebar: 56px`，搜索框不渲染）；1000px 宽时不折叠（`--sidebar: 264px`）。999px 下按一次 `Ctrl+B` 后展开为 264px，即手动选择优先于宽度推导。
- R11 面板按路径筛选：命令面板里输入 `beta/demo`、`work/design`、`alpha` 各只命中对应的那条「切换到 demo / design-system」，选项文案里仍只有仓库名，不显示路径。
- R5 提交区就地原因：暂存区非空而说明为空时 `[data-commit-blocker]` 显示「填写提交说明后即可提交」；点「全部取消暂存」后改为「先暂存要提交的文件」，同行换成「暂存区是空的」，提交区仍是 168px。失败原因（`[data-commit-error]`）走的是同一行同一块，见上一条的四档读数。
- R14 主题渲染：mock 的 `preview-theme` 切到 dark 后 `documentElement.dataset.theme = "dark"`，正文色 `rgb(232,239,235)`、标题栏 `rgb(21,27,24)`、rail `rgb(25,32,28)`；light 下分别是 `rgb(25,36,31)`、`rgb(255,255,255)`、`rgb(248,250,249)`。两套主题确实渲染出不同外观。
- 以上观察来自 mock 数据，不能代替真实 Git 仓库与安装包行为。Git 不可用时的诊断入口无法在预览里观察（mock 的 `getSettings` 固定返回 `git.available: true`），该行为只有下节第 5 条所述的 happy-dom 断言。

## 三、未验证项与缺口

1. **`cargo test` 未能运行（宿主环境缺口，非本次回归）**：测试二进制加载即 `STATUS_ENTRYPOINT_NOT_FOUND`（0xc0000139）。已排除陈旧产物（`cargo clean -p twiglane` 重编 56s 后同错）与 WebView2 缺失（运行时 156.0.4314.50 已安装），且该失败在本次改动之前的基线上即可复现。R17 的「cargo test 通过」一项记为**未验证**，不记为通过；`cargo clippy --all-targets` 只覆盖测试目标的编译与类型检查。
2. **Windows / macOS 自绘标题栏未实机复核**：拖拽、双击最大化、系统窗口按钮区避让、900×600 最小尺寸下的真实表现均无实机证据。R1、R16 在本记录中为**部分验证**（结构与尺寸有断言与浏览器观察，实机行为未知）。
3. **“默认深色”未在真实应用里观察到**：两套主题的渲染差异已可在预览中观察（见上节），但默认值来自 Rust 侧 `Theme::Dark` 与 `state.json`，而预览 mock 的默认主题是 light，因此只能核对 `index.html` 的 `data-theme="dark"`、Rust 侧默认值与已保存选择被读取的路径，没有真实应用里“开箱即深色”的观察。
4. **安装包与性能口径未重测**：本次未生成 NSIS/DMG，也未重跑 S/M/L 启动、内存、CPU 与协议验收。report.json 中这些条目仍停留在 2026-10-31 的 macOS 记录，不得当作本次候选的结果。
5. **仅由 happy-dom 断言覆盖、无浏览器观察的行为**：切换仓库在飞行中被拒（面板/标题栏菜单/rail 三个入口同源，含差异续读）、Git 不可用时诊断通知可关闭且指向设置运行环境分区、起始页独立诊断入口、以及本轮新增的「提交失败在提交区就地说明原因」（预览 mock 的 `commitChanges` 永远成功）。这些用真实 App 组件加受控 mock 断言（`tests/app-shell.spec.ts`、`tests/changes.spec.ts`），预览 mock 无法进入对应状态；失败原因行对 R5 高度的布局影响单独在浏览器里量过（见上节）。
6. **最小栏宽 160px 下「提交并推送」按钮被裁掉**：`.files` 是 `overflow-x: hidden`，栏宽 160px 时提交区动作行宽 244px，第二颗按钮的右边界正好压到栏右边界之外，可见宽度为 0。此时该动作只能从命令面板（`⌘/Ctrl+K` → 提交并推送）触发；R5 的高度门禁不受影响。这是最小栏宽 160px 的取舍，属 T5 的实现范围，T6 只记录不改实现。
